1. Executive Summary
Data Journey is a standalone, offline-first project and progress tracker designed to support a long-term journey of learning, project development and personal productivity. Its first use case is a 35-hour Data Analytics course planned as one hour per day for 35 days. The product must not be hardcoded around this challenge: it must support multiple projects and remain useful for learning, portfolio work, software development, research, business and other projects.
The application should be installable as a Progressive Web App (PWA), operate without an internet connection after its assets are available locally, keep user data locally, and provide robust export/import and backup/restore capabilities. The goal is a functional product—not a visual prototype.
2. Product Vision
Transform everyday work and learning activity into a structured record of progress, reflection and growth.
Track what was planned, what was done and how long it took.
Capture goals, tasks, issues, solutions and breakthroughs.
Make consistency visible through daily activity and streaks.
Provide useful analytics without requiring cloud services.
Keep the user's data portable and under the user's control.
Support the initial 35-day learning challenge while remaining useful indefinitely.

9. Recommended Technology & Architecture
HTML, CSS and modular JavaScript.
IndexedDB as the primary persistent local database.
localStorage only for small preferences where appropriate.
Service worker for offline caching.
Web App Manifest for installability.
Avoid MySQL, PostgreSQL, Firebase, Supabase, MongoDB or external APIs for core functionality.
A framework may be used only if it materially improves maintainability; avoid unnecessary complexity.
Separate UI, application logic, storage, analytics, services and utilities.

14. PWA Requirements
manifest.json with name, short name, description, start URL, display mode, theme/background colors and icons.
Service worker that caches application assets and supports offline operation.
Installable where supported by the browser/OS.
Do not falsely claim that opening index.html directly provides full PWA behavior; document local-server/HTTPS requirements accurately.
The installed app should open in an app-like window where supported.
15. Data Ownership, Backup & Recovery
All core data stays local.
Export all user data to a portable JSON backup.
Import must validate the backup before changing data.
Support restore/replace and, if practical, merge.
Rebuild indexes after import as needed.
Confirm before destructive operations.
Encourage periodic backups because clearing browser storage can remove local data.
16. Demo Data
Provide optional demo data showing multiple projects and all major record types.
Allow Load Demo Data and Clear Demo Data.
Clearly distinguish demo data from user data.

18. Progress Calculations
Learning projects: Actual Hours / Target Hours × 100.
General projects: primarily based on completed tasks and/or manual progress.
Never allow progress above 100%.
Document all calculation rules.
19. Search, Validation & Error Handling
Validate inputs and dates.
Prevent negative durations and impossible percentages.
Handle empty databases gracefully.
Handle invalid/corrupted imports gracefully.
Avoid duplicate imports where possible.
Do not expose raw JavaScript errors to normal users.
Provide useful empty states.
20. Privacy & Security
No mandatory login.
No mandatory internet connection.
No third-party tracking by default.
No external service required for core features.
Clearly document local-storage limitations.
21. Performance
Remain responsive with hundreds of projects and thousands of records.
Use IndexedDB indexes appropriately.
Avoid loading unnecessarily large datasets into the UI at once.
Keep calculations efficient.

24. Testing Requirements
Functional: projects, tasks, goals, issues, breakthroughs, daily records and time entries.
Persistence: reload and verify all records remain.
Backup: export, import, restore, merge and invalid-file handling.
Offline: disable internet and verify the application opens, reads, writes and calculates.
PWA: installation, launch, offline launch, cache behavior and update behavior.
Responsive: desktop, tablet and mobile.
Edge cases: empty database, large dataset, duplicates, zero-hour projects, completed/overdue projects and missing dates.

26. Installation & Sharing Model
The application should be distributable as a static project.
It should be deployable to GitHub Pages, Vercel, Netlify or another static host.
No backend server should be required for core functionality.
For full PWA behavior, use a suitable local server or HTTPS deployment as documented.
The same application should be usable on supported desktop and mobile browsers and installable as a PWA.

30. Non-Negotiable Development Rules
1. Do not build the application around only the 35-day course.
2. Do not introduce a backend unless there is a compelling reason.
3. Do not introduce authentication.
4. Do not make cloud storage mandatory.
5. Do not make internet access mandatory.
6. Do not sacrifice usability for excessive features.
7. Do not create unnecessary complexity.
8. Prioritize data integrity.
9. Prioritize user ownership of data.
10. Document every major feature.
11. Do not declare completion without testing offline functionality.
12. Do not declare completion without testing export/import.
31. Success Definition
The project is successful when the user can install Data Journey, create the 35-Day Data Analyst Journey, and use it every day for 35 days without needing an internet connection. At the end of the journey, the user should be able to clearly review what was worked on, how much time was spent, what was completed, what was difficult, what problems were solved, what was learned, what breakthroughs occurred, how consistent the user was, and what should happen next.
